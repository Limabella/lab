# 청록(靑錄) 프로젝트 작업 원칙

이 저장소를 수정할 때에는 기존 기록과 핵심 기능을 보존하면서 아래 헌장을 지속해서 적용한다.

## 청록 헌장

- 글은 관찰 → 분석 → 구현의 3단 흐름을 기본 골격으로 삼는다.
- 내용 비율은 연구형 65%, 개발형 30%, 블로그형 5%를 지향한다. 주제에 따라 조정할 수 있으나 근거와 구현이 기록성보다 우선한다.
- 평가 기준은 글 구조, 논리의 흐름, AI 활용 방식, 정량적 데이터화, 감정 균형, 문제의식, 정치성 절제, 공학적 구현, 인용과 출처의 아홉 항목이다.
- 1–5위는 현재 글의 강점, 6–9위는 다음 글에서 개선할 기준으로 해석한다.
- AI 결과는 그대로 붙이지 않는다. 출처, 수치, 코드와 맥락을 검증한 뒤 작성자의 논리로 재구성한다.

## 프로젝트 구조

- `index.html`: 오늘의 평가와 최근 기록
- `history.html`: 누적 기록 분석과 시각화
- `assets/styles.css`: 두 화면이 공유하는 디자인 시스템과 반응형 스타일
- `assets/charter.js`: 헌장 기준과 공통 표시 함수
- `assets/app.js`: 평가 정렬·저장·최근 기록 기능
- `assets/history.js`: 누적 통계·추이·매트릭스 기능
- `records.json`: 기록의 단일 원본. 이동하거나 초기화하지 않는다.
- `note/YYYY/YYYY-MM-DD.md`: 저장 시 생성되는 사람이 읽기 쉬운 날짜별 평가 노트
- `server.py`: 정적 파일과 `/api/records`를 제공하는 로컬 서버

## 작성 전 체크리스트

- 다루려는 문제와 독자가 분명한가?
- 관찰, 분석, 구현의 3단 흐름을 세웠는가?
- 주장마다 필요한 데이터와 1차 출처를 확보했는가?
- 구현 결과를 재현할 코드, 조건, 한계를 정리했는가?
- 연구형 65% · 개발형 30% · 블로그형 5%의 균형을 검토했는가?

## 작성 후 체크리스트

- 요약 → 문제 제기 → 원인 분석 → 해결이 자연스럽게 이어지는가?
- 수치, 인용, 이미지, AI 생성 내용의 출처와 사실을 검증했는가?
- 사회적 맥락과 공학적 구현이 실제로 연결되는가?
- 감정적 단정이나 불필요한 정치적 해석을 줄였는가?
- 모바일과 키보드 환경에서 핵심 기능을 사용할 수 있는가?
- 기존 `records.json`의 기록과 `/api/records` 호환성을 보존했는가?
- 날짜별 Markdown 노트가 구조화 기록과 같은 내용을 담는가?

## 변경 원칙

- 데이터 파일을 수정하기 전 형식과 기존 내용을 먼저 확인한다.
- 화면 문자열은 HTML 삽입 전에 이스케이프하며 서버 입력도 검증한다.
- 외부 라이브러리는 기능상 꼭 필요할 때만 추가한다.
- 변경 후 Python 문법, JavaScript 문법, API 읽기·쓰기, 주요 화면의 반응형 레이아웃을 확인한다.
